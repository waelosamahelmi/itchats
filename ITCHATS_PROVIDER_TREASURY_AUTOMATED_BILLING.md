# itChats Provider Treasury & Automated AI Cost Settlement
## Production Feature Specification

**Project:** itChats  
**Repository:** `waelosamahelmi/itchats`  
**Feature:** Provider Treasury, Revenue Allocation, Usage Cost Accounting & Automated Provider Settlement  
**Status:** Implementation specification  
**Version:** 1.0  
**Date:** 2026-07-24

---

# 1. Executive Summary

itChats should operate as the merchant that charges the customer once, while the platform automatically tracks, reserves, reconciles, and settles the costs generated by Alibaba Cloud and any future AI providers.

The desired business flow is:

```text
Customer
   │
   │ pays subscription / credits / add-on
   ▼
Stripe
   │
   ▼
itChats Revenue
   │
   ├── Provider Cost Reserve
   ├── Refund / Dispute Reserve
   ├── Tax Reserve
   ├── Stripe Fee Accounting
   └── Available Profit
            │
            ▼
       Business Payout
```

Provider settlement is separate:

```text
AI usage occurs
     │
     ▼
itChats records exact/estimated provider cost
     │
     ▼
Provider liability increases
     │
     ▼
Alibaba / OpenRouter / other provider
auto-charges the configured company payment method
     │
     ▼
itChats reconciles provider invoice/payment
     │
     ▼
Provider liability becomes settled
```

The crucial concept is:

> **Do not try to split every customer Stripe charge directly to Alibaba.**
>
> Instead, itChats must maintain a real-time internal treasury ledger that knows how much of the collected money is revenue, how much is owed to providers, and how much is actually safe to withdraw as profit.

This architecture is safer, more scalable, easier to reconcile, and works across multiple AI providers.

# 2. Important Payment Architecture Decision

## 2.1 Do not depend on Stripe Connect for AI provider settlement

Stripe Connect is designed to move funds to Stripe Connected Accounts.

Alibaba Cloud, OpenRouter, and similar AI providers are not automatically connected accounts of itChats.

Therefore, this is **not** the production architecture:

```text
Customer payment
   ├── €8 directly to Alibaba via Stripe Connect
   └── €22 directly to itChats
```

Do not build the platform around this assumption.

---

## 2.2 Do not depend on a Stripe Issuing virtual card for Alibaba Cloud

As of July 2026, Alibaba Cloud's published payment-method documentation says that prepaid, virtual, and gift cards are not supported for its standard bank-card verification flow.

Therefore:

```text
Stripe Payments
    ↓
Stripe Issuing virtual card
    ↓
Alibaba Cloud
```

must **not** be considered the production Alibaba settlement path.

Stripe Issuing can still be useful for other providers that explicitly accept the card type, but every provider must have a payment capability flag before any automated card strategy is enabled.

---

## 2.3 Recommended production settlement path

For Alibaba:

```text
Customer
   ↓
Stripe
   ↓
itChats Stripe balance
   ↓
automatic Stripe payout
   ↓
itChats business bank account
   ↓
normal business debit/credit card or supported payment method
   ↓
Alibaba Cloud automatic PAYG deduction
```

Alibaba handles automatic PAYG collection from its configured supported payment method when billing thresholds are reached and/or during settlement periods.

The exact timing of provider settlement is **not** tied to the exact customer transaction.

The itChats treasury ledger bridges that timing mismatch.

# 3. Goals

The feature must make itChats financially self-aware.

The platform must always be able to answer:

```text
How much have users paid us?
How much has Stripe charged us?
How much AI usage have we consumed?
How much do we currently owe providers?
How much provider cost has already been settled?
How much should we reserve for refunds/disputes?
How much should we reserve for tax?
How much money is actually safe to withdraw?
Which users/models/features are profitable?
Which providers are becoming expensive?
Are we about to run out of provider funding?
```

The feature should require minimal day-to-day manual management.

---

# 4. Non-Goals

This feature should **not**:

- Treat gross Stripe balance as profit.
- Depend on manual spreadsheets.
- Trust cost calculations performed in the frontend.
- Put provider API keys in the browser.
- Let a customer invoke an expensive model without server-side authorization.
- Allow usage to be recorded without a corresponding cost event.
- Assume all providers bill the same way.
- Assume provider invoices arrive immediately.
- Assume Stripe and provider settlement currencies always match.
- Automatically withdraw all available Stripe funds.
- Allow a provider outage or billing API failure to corrupt customer balances.
- Couple the customer pricing model directly to provider invoicing mechanics.

# 7. Core Accounting Model

Use a **double-entry-style immutable ledger** for money and liabilities.

Do not simply store:

```text
user.balance = 17.40
providerCost = 5.20
```

and mutate those values.

Instead, every financial event should create ledger entries.

Derived balances can be cached, but the ledger remains the source of truth.

---

# 8. Treasury Buckets

At minimum, model the following internal treasury buckets.

## 8.1 Customer Revenue

Money successfully collected from customers.

```text
CUSTOMER_REVENUE
```

## 8.2 Stripe Fee Liability / Expense

```text
PAYMENT_PROCESSING_FEES
```

## 8.3 Provider Liability

Money economically owed because provider usage has occurred but has not necessarily been paid yet.

```text
PROVIDER_PAYABLE
```

This should be broken down per provider:

```text
PROVIDER_PAYABLE:ALIBABA
PROVIDER_PAYABLE:OPENROUTER
PROVIDER_PAYABLE:OTHER
```

## 8.4 Provider Settled Cost

Provider invoices or charges already paid.

```text
PROVIDER_SETTLED
```

## 8.5 Refund Reserve

```text
REFUND_RESERVE
```

## 8.6 Dispute Reserve

```text
DISPUTE_RESERVE
```

## 8.7 Tax Reserve

```text
TAX_RESERVE
```

Tax logic should be configurable and should not be hardcoded into the general ledger.

## 8.8 Available Profit

A derived amount.

Never store `available_profit` as the primary source of truth.

Calculate it.

Example:

```text
safe_withdrawable =
    settled_customer_cash
  - provider_payable
  - pending_provider_cost_buffer
  - refund_reserve
  - dispute_reserve
  - tax_reserve
  - unsettled_payment_fees
  - operational_minimum_cash_buffer
```

# 9. Example

Customer purchases a €30 plan.

Assume:

```text
Customer paid                       €30.00
Estimated Stripe fee                € 1.20
Provider reserve                    € 8.00
Refund/dispute reserve              € 1.00
Tax reserve                         € 4.00
Operational cash buffer allocation  € 1.00
```

The admin dashboard should show:

```text
Gross collected                     €30.00
Payment processing reserve          -€1.20
Provider payable                    -€8.00
Refund/dispute reserve              -€1.00
Tax reserve                         -€4.00
Operational reserve                 -€1.00
──────────────────────────────────────────
Safe contribution / margin          €14.80
```

Then suppose the user actually consumes only €4.10 of provider cost during that period.

The provider liability reserve can be re-evaluated according to the product's pricing policy.

The platform must distinguish:

```text
forecast provider liability
actual accrued provider cost
settled provider cost
```

These are different concepts.

```text

```

They are not the same thing.

Example:

```text

```

```text

```

The customer-credit ledger should be separate from the treasury cash ledger.

```text

```

# 12. Usage Event Lifecycle

Every paid AI call must follow a server-side lifecycle.

```text
1. Request arrives
2. Authenticate customer
3. Resolve subscription/credits
4. Resolve model/provider
5. Calculate pre-flight estimated cost
6. Validate margin policy
7. Reserve user credits
8. Reserve provider exposure
9. Invoke provider
10. Capture actual provider usage
11. Calculate actual cost
12. Finalize user charge
13. Finalize provider liability
14. Release unused reservation
15. Persist usage record
16. Emit analytics event
```

Do not allow:

```text
frontend → Alibaba directly
```

for anything billed to the user.

Correct:

```text
frontend
  ↓
itChats API
  ↓
authorization + price quote + reserve
  ↓
provider router
  ↓
Alibaba
```

# 13. Pre-Flight Cost Quote

Before an expensive action, the backend should create a cost quote.

Example response:

```json
{
  "quoteId": "quote_123",
  "feature": "ai_chat",
  "provider": "alibaba",
  "model": "qwen3.5-flash",
  "estimatedProviderCostMinor": 2,
  "estimatedCustomerPriceMinor": 8,
  "currency": "EUR",
  "marginPercent": 75,
  "expiresAt": "2026-07-24T12:01:00Z"
}
```

For token-based chat, the exact cost is not fully known before completion.

Therefore use:

```text
estimated cost → reserve → actual cost → settlement
```

# 18. Margin Guard

Before executing any paid AI request:

```text
grossMargin =
(customerPrice - estimatedProviderCost - allocatedVariableFees)
/
customerPrice
```

Configurable policy:

```text
targetGrossMargin: 70%
warningGrossMargin: 55%
hardMinimumGrossMargin: 35%
```

Example behavior:

```text
margin ≥ 70%       → allow
55–69.99%          → allow + analytics warning
35–54.99%          → configurable allow/block
<35%               → block or route to cheaper provider
negative margin    → always block unless explicitly admin-approved
```

Admin can override individual models.

# 23. Alibaba Cloud Strategy

Use Alibaba PAYG billing as provider-level settlement.

Recommended flow:

```text
itChats uses Alibaba model
      ↓
itChats immediately records estimated/actual cost
      ↓
PROVIDER_PAYABLE:ALIBABA increases
      ↓
Alibaba accumulates billable usage
      ↓
Alibaba auto-charges configured supported payment method
      ↓
webhook/API/polling/reconciliation detects settlement
      ↓
PROVIDER_PAYABLE:ALIBABA decreases
      ↓
PROVIDER_SETTLED:ALIBABA increases
```

Do not wait for Alibaba to charge the card before recording the liability.

Economic cost exists when the AI request is consumed.

# 29. Minimum Cash Buffer

Introduce:

```text
operational_minimum_cash_buffer
```

Never allow safe withdrawal to reduce liquid cash below this threshold.

Possible configuration:

```text
max(
  fixedMinimum,
  7DayProviderForecast,
  14DayProviderForecast * safetyMultiplier
)
```

Example:

```text
fixed minimum              €500
7-day provider forecast    €720
14-day forecast            €1,250
safety multiplier          1.20

minimum cash buffer = €1,500
```

# 32. Refund Handling

Refunds must reverse customer economics without deleting history.

Example:

```text
Customer paid €30
Provider usage already cost €4
Customer receives full €30 refund
```

The €4 provider cost remains real.

Margin becomes negative.

Record:

```text
customer revenue reversal
refund expense
provider cost remains
```

Do not delete original usage records.

---

# 33. Disputes / Chargebacks

When Stripe reports a dispute:

```text
1. Freeze the disputed payment value in treasury calculations.
2. Mark related revenue as at risk.
3. Do not reverse provider cost.
4. Optionally restrict additional high-cost usage for that user.
5. Recalculate safe-withdrawable.
```

If dispute is lost:

```text
revenue loss becomes final
```

If won:

```text
release dispute reserve
```

# 34. Negative Balance Protection

A user should never be able to generate unlimited provider cost because of request concurrency.

Required controls:

- Atomic wallet reservations.
- Database transactions.
- Per-user concurrency limits.
- Per-feature maximum in-flight spend.
- Daily user usage limits.
- Plan limits.
- Abuse detection.
- Rate limits.
- High-cost model limits.
- Provider-wide emergency cutoff.
- Admin kill switch.

# 41. Reconciliation Engine

Provider usage reported by itChats and provider billing will sometimes differ.

# 53. AI Request Integration Example

Pseudo-code:

```ts
async executeChat(userId: string, input: ChatRequest) {
  const route = await providerRouter.select({
    capability: 'chat',
    userId,
    requestedModel: input.model,
  });

  const quote = await pricing.quote({
    userId,
    provider: route.provider,
    model: route.model,
    request: input,
  });

  await marginGuard.assertAllowed(quote);

  const reservation = await usage.reserve({
    userId,
    quote,
  });

  try {
    const result = await route.client.chat(input);

    const actual = await usage.finalize({
      reservationId: reservation.id,
      providerResult: result,
    });

    return {
      result: result.data,
      usage: actual.customerUsageView,
    };
  } catch (error) {
    await usage.fail({
      reservationId: reservation.id,
      error,
    });

    throw error;
  }
}
```

# 59. Currency Handling

Never use floating-point numbers for money.

Store minor units:

```text
€12.34 → 1234
$0.0012 → not representable with 2-decimal minor unit
```

AI cost can be much smaller than one cent.

Therefore create a high-precision internal cost unit.

Recommended:

```text
microunits
```

Example:

```text
1 EUR = 1,000,000 cost micros
```

or use fixed-precision decimal columns.

Recommended database approach:

```text
numeric(24, 12)
```

for provider unit cost calculations,

then use integer minor units for Stripe-facing payment amounts.

mark amount settled

reconcile difference

# 115. Accounting Philosophy

The system must distinguish:

```text
CASH
REVENUE
CUSTOMER CREDIT
PROVIDER COST
PROVIDER LIABILITY
PROVIDER PAYMENT
TAX
REFUND
DISPUTE
PROFIT
```

These are not interchangeable.

This distinction is the difference between:

```text
"We have €20,000 in Stripe"
```

and:

```text
"We have €20,000 liquid, of which €6,300 is already economically committed,
and €13,700 remains before other operating costs."
```

# 117. Definition of Done

This feature is complete when:

- All customer payments are processed server-side through Stripe.
- Stripe webhooks are signature-verified and idempotent.
- Every paid AI request creates a usage record.
- Every AI request is priced before execution.
- Every paid AI request reserves customer funds/credits atomically.
- Every provider request records provider exposure.
- Actual provider cost is finalized whenever available.
- Provider liabilities are tracked independently of provider charge timing.
- Alibaba is paid using a supported company payment method rather than depending on a Stripe virtual card.
- Provider invoices/payments can be reconciled.
- Refunds and disputes correctly affect treasury calculations.
- Admin can see real revenue, real provider cost, margin, reserves, and safe-withdrawable cash.
- Admin can pause expensive providers/models.
- Promo/free usage is cost-capped.
- Provider pricing is versioned.
- Historical profitability does not change when pricing tables change.
- No provider API key is exposed to the browser.
- No customer can create unlimited provider cost through concurrency or retries.
- The system can survive duplicated Stripe webhooks.
- The system can survive provider retries/fallbacks without double-charging the customer.
- Treasury has automated alerts and daily snapshots.
- Finance calculations are tested with deterministic unit tests.
- itChats can answer “How much money is actually mine?” without a spreadsheet.

# 118. Critical Implementation Rules

1. **Webhook truth, not redirect truth.**
2. **Ledger entries are immutable.**
3. **Provider cost begins when usage occurs, not when the bill is paid.**
4. **Customer credits are not cash.**
5. **Gross Stripe balance is not profit.**
6. **Every provider request is metered.**
7. **Every paid request is reserved before execution.**
8. **Every provider price is versioned.**
9. **Every financial write is idempotent.**
10. **Every high-cost pathway has a circuit breaker.**
11. **Free/promotional usage has a provider-cost ceiling.**
12. **Financial calculations are deterministic; AI only explains them.**
13. **Do not depend on a Stripe virtual card for Alibaba Cloud.**
14. **Never expose provider keys client-side.**
15. **Do not withdraw based only on Stripe's displayed balance.**
